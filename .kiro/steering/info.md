## Цель проекта

Проект ANIMATIONAPP представляет собой приложение для рисования пиксельарта, разработанное на Godot 4.6. В дальнейшем планируется расширение функционала по этапам:
1.  Этап рисования (текущий).
2.  Этап создания из слоёв полигонов и их скелетной анимации.
3.  Этап пикселизации и постобработки.

## Текущее состояние архитектуры

**СТАТУС: Активная миграция на новую архитектуру**

Проект находится в активной фазе рефакторинга. Старая архитектура на основе синглтонов заменяется на современную модульную систему с EventBus, AppState и Services.

Зоны ответственности должны быть хорошо определены. Если UI - То только UI, если Core - то Core и т.д. Не миксовать без надобности

Если что-то является God-object на твой взгляд, обязательно дай знать об этом и предложи путь исправления (распределения обязанностей). К примеру layers_panel.gd была Год-обджектом, она создавала слои, отвечала за их UI отображени и их логическое поведение. При создании слоя она обе стороны логики прописывала. В то время, как должна отвечать согласно названию - Панель слоёв = создание, удаление и UI отображение слоёв на панели (то есть только визуал). Да, она удобна для микса логики, но правильнее будет передавать сигналы или дёргать сервисы/что-то стороннее.
Принцип: моя зона ответственности = моё имя. Конечно, задуряться не надо, и layers_panel к примеру, вполне понятно описывает зону ответственности, не обязательно брать и дописывать layers_ui_order_manager и т.д. 
Соизмеримость!

### Принципы новой архитектуры

1. **EventBus** - все компоненты общаются через события, а не прямые вызовы
2. **AppState** - централизованное реактивное состояние с автоматическими уведомлениями
3. **Services** - бизнес-логика вынесена в отдельные сервисы
4. **Слабая связанность** - компоненты не знают друг о друге напрямую
5. **Высокая связность** - каждый модуль отвечает за одну область

### Ключевые компоненты новой архитектуры

**1. EventBus (globals/event_bus.gd)**
- Централизованная система событий
- Все компоненты подписываются на события вместо прямых вызовов
- События: tool_selected, primary_color_changed, layer_created, etc.

**2. AppState (globals/app_state.gd)**  
- Реактивное состояние с автоматическими уведомлениями
- Свойства: current_tool, primary_color, secondary_color, active_layer_id
- При изменении автоматически эмитит события через EventBus

**3. Services (globals/services.gd)**
- Service Locator для доступа к бизнес-логике
- Доступ: `Services.tool.select_tool()`, `Services.layer.create_layer()`
- Все сервисы регистрируются при инициализации

**4. LayerService - система на int ID:**
- **КРИТИЧНО**: Вся логика работает через уникальные int ID
- Имена слоёв - только UI labels для пользователя
- Пользователь может назвать 100 слоёв одинаково - логика не сломается
- Маппинг: `layer_id (int) -> layer_data (Dictionary)`
- Автоинкремент ID через `_next_layer_id`

**5. Мигрированные компоненты:**

- **tool.gd** - кнопки инструментов используют EventBus для уведомлений и AppState для состояния
- **swatch.gd** - цветовые образцы работают через ColorService и EventBus  
- **assets/swatch_picker.gd** - синхронизируется с новой цветовой системой
- **assets/globals/cursor.gd** - получает цвета из AppState через EventBus
- **assets/ui_components/layers/layers_panel.gd** - полностью на int ID, маппинг через метаданные
- **draw_container.gd** - интегрирован с LayerService через int ID
